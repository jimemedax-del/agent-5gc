### R1 → R2：调整依据与继承关系

- **依据**：用户转述导师要求建立可编排网络功能环境，调研开源网络软件、5GC 开放能力和 Linux/OVS 封装；小实验覆盖流量识别、QoS 控制、代理转发、流量引导和边缘服务接入。

- **继承**：Compose、单节点/三节点 k3s、固定 Profile、镜像与版本锁定、UE 业务验收、测量脚本和已归档故障证据。

## 当前研究定位

目标是面向业务需求，构建一套安全、可解释、可验证的 5GC 与 CNF 服务链编排闭环：

```text
业务需求
→ 结构化意图
→ CNF 功能目录、状态与约束
→ 规则/优化规划器
→ 受控服务链方案与校验
→ Kubernetes / free5GC / CNF
→ UE 端到端验证与性能反馈
```

核心分工：

- **Agent**：在后续阶段理解业务需求、调用受控工具、解释并协调重规划。
- **规则/优化规划器**：根据功能依赖、资源、网络和业务约束生成服务链方案。
- **校验器与执行适配器**：限制镜像、配置、网络接入和权限范围，负责可执行性与审计。
- **free5GC/UERANSIM**：提供真实UE接入、会话和基础用户面。
- **CNF 服务链**：完成流量识别、QoS控制、代理转发、流量引导和边缘服务接入。

Agent 不直接参与 5G 信令，不生成任意 YAML、镜像地址或 Helm Values。首版先手工验证服务链，再实现确定性编排，最后接入 Agent。

## 为什么需要从单 UPF 基线走向 CNF 服务链

单 UPF 场景中的“低时延业务就选 edge UPF”选择空间很小。仅完成“自然语言 → Agent → Helm → free5GC”也无法证明业务流量被识别、控制和引导。

更合理的研究问题是：

> 在已有5GC接入与用户面基础上，如何根据业务需求选择并配置流量识别、QoS控制、代理转发、流量引导和边缘接入等CNF，使服务链满足约束并可端到端验证？

后续的多 UPF、路径选择和边缘放置可作为服务链编排的扩展变量，不是首个实验的前提。

## 论文价值的最低门槛

论文的主要贡献应是“受约束的意图驱动 CNF 服务链编排方法”，而不是“调用了一个大模型”。建议包含：

1. **问题建模**：业务功能需求、功能依赖、资源和网络能力等硬约束，与低时延、低成本等偏好的区分。
2. **方法设计**：资源、路径与功能链感知的规则/优化算法；Agent 仅提供语义理解与可解释协调。
3. **安全机制**：目录白名单、结构化输出、确定性校验和失败反馈。
4. **真实验证**：在 free5GC、UERANSIM、Kubernetes 和实际CNF服务链上验证，而不止于纯仿真。
