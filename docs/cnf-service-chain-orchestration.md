# 面向业务需求的 CNF 服务链编排

> 最后更新：2026-10-10  
> 状态：方向已根据导师交流调整；本文记录设计与待验证项，不代表功能已经实现。

## 目标与边界

项目以已验证的 free5GC、UERANSIM 与 Kubernetes 三节点环境为接入和用户面底座，进一步构建可编排的网络功能（CNF）环境。目标是：面对业务需求，选择并配置流量识别、QoS 控制、代理转发、流量引导和边缘服务接入等功能，使 UE 业务流量经过可观测、可验证的服务链。

```text
业务需求
→ 识别业务与约束
→ 选择/配置 CNF 服务链
→ free5GC 提供 UE 接入与用户面基础转发
→ 代理、引导与边缘服务处理实际业务流量
→ 测量端到端效果并反馈
```

本模块不把所有 5GC 网元视为可任意串联的数据面功能。AMF、AUSF、UDM/UDR、NRF、NSSF、PCF、SMF 和 UPF 仍按其 5GC 职责协作；业务数据的基础路径为 `UE → gNB → UPF → 数据网络`。Agent 是后续的受约束决策层，不是当前最小实验的前提。

## 与既有平台的关系

| 范围 | 当前结论 | 本模块中的作用 |
|---|---|---|
| UE、gNB、AMF、SMF、UPF | 已完成注册、PDU Session 与用户面连通验证 | 提供真实 UE 接入和基础用户面 |
| PCF | 已部署，QoS 策略是否产生可测用户面效果尚未验证 | 候选 QoS 策略控制能力 |
| NEF | 已部署，源码含 Traffic Influence 接口 | 候选应用/业务需求入口，需验证端到端效果 |
| Kubernetes 三节点与固定 Profile | 已验证可重复部署 | 承载既有 5GC 与后续新增 CNF |
| 流量识别、代理转发、可观测流量引导 | 尚未建立 | 本模块需要补充的核心能力 |

已有 5GC 基线不需要重做。此前以 SMF/UPF 实例选择为中心的设想保留为后续扩展决策维度，但不再单独构成当前主线。

## 功能目录与实现原则

导师提出的功能先按逻辑能力登记；首版不要求每项都对应独立容器，但必须清楚记录其实际实现、接口、位置和验证证据。

| 逻辑功能 | 首版可行实现 | 作用与验收要点 |
|---|---|---|
| 流量识别 | 代理按目标地址、端口、HTTP 路径或请求头匹配 | 能将至少两类测试业务稳定分类 |
| QoS 控制 | 先用 Linux `tc` 或 OVS 形成可测差异；并调研 PCF→SMF→UPF 联动 | 在受控竞争流量下观察限速、优先级或带宽差异 |
| 代理转发 | Nginx、Envoy 或等价开源代理容器 | UE 流量可经代理到达后端服务，并有日志证明 |
| 流量引导 | 代理路由规则或 Linux/OVS 策略路由；NEF/SMF 能力后续验证 | 不同业务可到达不同目标服务或路径 |
| 边缘服务接入 | Kubernetes 中部署HTTP、视频模拟或 iperf3 测试服务 | UE 可通过服务链访问目标服务 |

PCF 是策略决策功能，不是通用流量识别器或应用代理；UPF 提供基础用户面转发，不自动保证业务经过新增 CNF。任何新增功能都必须有明确的流量接入和转发规则。

## 最小实验

首个实验聚焦手工服务链，不引入 Agent：

```text
UE → gNB → UPF → 代理 CNF → 边缘服务 A / 默认服务 B
```

建议以两个可区分业务为输入，例如“低时延业务”和“普通业务”。代理依据规则进行分类和引导；QoS 控制在可观察的转发点实施。验收至少包括：

1. UE 流量确实经 UPF、代理和目标服务，而非绕过服务链；
2. 两类业务被稳定识别并引导至预期服务；
3. QoS 规则在受控条件下产生可重复测量的差异；
4. 保存请求日志、路径证据、RTT、吞吐、丢包和资源指标。

UERANSIM 不模拟真实无线调度，因此首版的 QoS 结论限定为当前虚拟网络与服务链中的可测效果，不能宣称无线侧 QoS 保障。

## 实施路线与产出

| 阶段 | 目标 | 主要产出 |
|---|---|---|
| 1. 功能调研 | 为每项逻辑功能选择开源实现或 5GC 开放能力 | 功能目录、接口与依赖矩阵 |
| 2. 手工服务链 | 打通 UE→UPF→代理→边缘服务 | 受控配置、端到端证据 |
| 3. QoS 与引导验证 | 加入两类业务、策略和测量 | 可重复数据与结果汇总 |
| 4. 确定性编排 | 根据结构化需求生成受控服务链配置 | 规则、校验器和测试 |
| 5. Agent | 在确定性能力之上完成意图理解、工具调用、记忆与重规划 | Agent 工作流与对照实验 |

后续实现时，配置和部署资产放入 `infra/cnfs/`，脚本放入 `scripts/`，原始实验材料放入 `results/<日期>-cnf-service-chain-<实验名>/`。需要自行实现的控制器或服务开始开发时，再创建 `services/`；不要预先建立空目录。故障细节仍写入 [problem solve.md](../problem%20solve.md)。

## 待验证事项

- 哪些现有 free5GC PCF/NEF 接口能在当前版本和配置中形成完整的业务效果；
- 代理、QoS 控制和流量引导的具体开源实现及其容器化方式；
- 新增 CNF 放置在 UPF 后、边缘节点或独立节点时的网络接入方式；
- 导师对首版“编排”是否要求运行时创建实例，还是选择并配置预部署实例；
- 业务类别、QoS目标、拓扑差异和评价指标的具体定义。
