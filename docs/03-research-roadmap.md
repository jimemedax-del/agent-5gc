# 研究路线：基于 Agent 的 5GC 与 CNF 服务链编排

> 最后更新：2026-10-10
> 状态：研究方向已根据导师交流调整；其中未落地部分均为计划，不代表已实现。

## 当前研究定位

目标是面向业务需求，构建一套安全、可解释、可验证的 5GC 与 CNF 服务链编排闭环：

```text
业务需求
→ 结构化意图
→ CNF 功能目录、状态与约束
→ 规则/优化规划器
→ 受控服务链方案与校验
→ Kubernetes / free5GC / CNF
→ UE 端到端验证与性能反馈
```

核心分工：

- **Agent**：在后续阶段理解业务需求、调用受控工具、解释并协调重规划。
- **规则/优化规划器**：根据功能依赖、资源、网络和业务约束生成服务链方案。
- **校验器与执行适配器**：限制镜像、配置、网络接入和权限范围，负责可执行性与审计。
- **free5GC/UERANSIM**：提供真实UE接入、会话和基础用户面。
- **CNF 服务链**：完成流量识别、QoS控制、代理转发、流量引导和边缘服务接入。

Agent 不直接参与 5G 信令，不生成任意 YAML、镜像地址或 Helm Values。首版先手工验证服务链，再实现确定性编排，最后接入 Agent。

## 当前阶段

当前进度：Compose、单节点 k3s/Helm 与三节点 Flannel 单网络基线均已完成。首个固定 Profile 已完成受控重部署和严格业务验收；当前进入 CNF 功能调研和最小服务链设计，Agent 尚不进入编码阶段。详细范围见 [CNF 服务链编排模块](cnf-service-chain-orchestration.md)。

- [已验证] Docker Compose 与单节点 k3s/Helm 的 Single UPF 业务闭环；k3s 环境重启后可自动恢复。
- [已验证] 第二台独立 Ubuntu VM 从零重建了相同版本的 k3s/Helm/Single UPF 基线，并完成 UE 端到端出网。
- [已验证] 三节点 Kubernetes 已完成：VM1 承载控制面与 MongoDB、VM2 承载带 `gtp5g` 的 UPF、VM3 承载 UERANSIM；20/20 次注册和 PDU Session 成功。
- [已验证] `free5gc-3node-no-multus-v1` 已锁定 Chart、补丁、受控 Values、17 个镜像 Digest 与 15 个工作负载；一次完整重部署后，核心网 Revision 14、UERANSIM Revision 6，注册、会话和 TUN Ping 均通过。
- [归档限制] 高负载复测中补丁 UPF 未再 Panic，但 SMF 曾 OOM 重启；完整吞吐和长期稳定性仍待验证，不作为当前主线继续追查。
- [尚未开始] CNF 功能目录、手工服务链、QoS与流量引导验证、确定性服务链编排和 Agent 工作流。

## 为什么需要从单 UPF 基线走向 CNF 服务链

单 UPF 场景中的“低时延业务就选 edge UPF”选择空间很小。仅完成“自然语言 → Agent → Helm → free5GC”也无法证明业务流量被识别、控制和引导。

更合理的研究问题是：

> 在已有5GC接入与用户面基础上，如何根据业务需求选择并配置流量识别、QoS控制、代理转发、流量引导和边缘接入等CNF，使服务链满足约束并可端到端验证？

后续的多 UPF、路径选择和边缘放置可作为服务链编排的扩展变量，不是首个实验的前提。

## 建议实施顺序

### 1. 基线可复现

- 固化 Compose、free5GC、UERANSIM、gtp5g 与配置版本。
- 从干净环境重现注册、PDU Session、用户面联通。
- 学会观察 AMF/SMF/UPF 日志和 PFCP/gtp5g 动态规则。

### 2. Kubernetes 与多节点网络

- [已验证] 固定 Single UPF Profile 已部署至单节点 k3s，并完成空白 VM 复现和重启恢复测试。
- [已验证] 已在同宿主机三台 VM 上完成控制面、UPF 与 RAN/UE 的逻辑角色分离，并通过端到端业务验收。
- [待验证] 引入 Multus、第二网卡和实际 N6 网络；通过真实拓扑或受控仿真构造可测量的 edge/core 路径差异。

### 3. CNF 功能目录与手工最小服务链

- 为流量识别、QoS控制、代理转发、流量引导和边缘服务接入建立功能目录，记录镜像、接口、资源、依赖、部署位置、状态和指标。
- 先手工打通 `UE → gNB → UPF → 代理 CNF → 边缘服务`，以流量日志和测量数据证明业务没有绕过服务链。
- 在受控竞争流量下验证分类、引导和QoS效果；PCF/NEF开放能力逐项验证，不因组件已部署而默认能力已生效。

### 4. 确定性编排与 Agent

- 服务链手工验证后，使用受控配置与确定性校验器完成部署、更新、审计和回滚。
- 数据结构稳定后，再以Python函数或LangGraph实现Agent工作流：解析需求 → 查功能目录/状态 → 规划服务链 → 校验 → 执行 → 测量 → 有限重规划。

## 论文价值的最低门槛

论文的主要贡献应是“受约束的意图驱动 CNF 服务链编排方法”，而不是“调用了一个大模型”。建议包含：

1. **问题建模**：业务功能需求、功能依赖、资源和网络能力等硬约束，与低时延、低成本等偏好的区分。
2. **方法设计**：资源、路径与功能链感知的规则/优化算法；Agent 仅提供语义理解与可解释协调。
3. **安全机制**：目录白名单、结构化输出、确定性校验和失败反馈。
4. **真实验证**：在 free5GC、UERANSIM、Kubernetes 和实际CNF服务链上验证，而不止于纯仿真。
5. **对照实验**：人工固定部署、规则法、贪心/优化基线、Prompt-only LLM，以及完整方案。

可比较的指标包括：计划合法率、服务链部署成功率、规则生效率、UE注册/PDU Session成功率、RTT、吞吐量、丢包、资源利用率、规划时延和模型调用成本。

## WirelessAgent 文献带来的启发

Tong 等 *WirelessAgent: Large Language Model Agents for Intelligent Wireless Networks*（2025）说明了“LLM + 知识库 + 外部工具”的结构化网络智能体思路。

- [可借鉴] Perception—Memory—Planning—Action 职责划分、Global State、知识库、工具调用轨迹、Prompt-only 与规则方法对照。
- [不可照搬] 该文主要处理切片带宽分配和仿真场景，没有解决 Helm、Kubernetes、gtp5g、Multus、回滚与真实 5GC 部署约束。
- [项目影响] Agent 应使用固定工作流与结构化输出；专业计算和安全约束由规划器、校验器承担。
